MCP — 模型上下文协议

AI 世界的 "USB-C"：连接模型与工具的开放标准
现状数据（2026-03）
MCP 于 2024 年 11 月由 Anthropic 发布，2025 年 12 月捐赠给 Linux 基金会。目前有 10,000+ 活跃 Server、9700 万月度 SDK 下载、1,200+ 经质量认证的实现。OpenAI 和 Google DeepMind 均已采用。

三种传输方式

方式命令参数适用场景推荐度
HTTP--transport http远程服务、生产环境★★★ 首选
SSE--transport sse流式数据、实时推送★★☆ 次选
Stdio--transport stdio本地进程、直接系统访问★★☆ 本地
 
# HTTP — 生产环境推荐
claude mcp add --transport http notion https://mcp.notion.com/mcp
claude mcp add --transport http secure-api https://api.example.com/mcp \
  --header "Authorization: Bearer your-token"

# SSE — 流式数据
claude mcp add --transport sse asana https://mcp.asana.com/sse

# Stdio — 本地进程
claude mcp add --transport stdio \
  --env AIRTABLE_API_KEY=YOUR_KEY airtable \
  -- npx -y airtable-mcp-server

Chapter 02

多 Agent 协作架构

四种协作模式 · 上下文压缩 · 长任务状态管理

四种协作模式

🔗 顺序链（Sequential）
A → B → C，前者输出作为后者输入。
适合：数据处理流水线、文档生成
⚡ 并行执行（Parallel）
多 Agent 同时处理不同子任务。
适合：大规模数据分析、独立模块开发
🎯 主管路由（Supervisor）
Orchestrator 决定调用哪个子 Agent。
适合：客服路由、多领域专家系统
🤝 层级（Hierarchical）
多层嵌套的 Orchestrator。
适合：复杂企业流程、研究系统

上下文腐烂（Context Rot）警告

关键研究发现（Chroma Research, 2025，18 个模型测试）
大多数模型实际只有效使用上下文的 10-20%。声称 200K tokens 的模型，通常在 130K 时已变得不可靠。更多内容 ≠ 更好结果。

注意力分布规律（Lost in the Middle）

上下文位置       注意力强度
─────────────────────────────────
开头 (0-10%)    ████████████  最高
中间 (10-90%)   ██            最低 ← 放"可查阅资料"
结尾 (90-100%)  ██████████    次高 ← 放"最新问题"

长任务最佳实践

#策略说明
1精选而非填满高质量少量 tokens > 低质量大量 tokens
2关键信息置首尾规则放开头，最新问题放结尾
3定期压缩检查点每 N 轮自动摘要，保留决策记录
4外部存储持久化重要发现写文件/数据库，跨轮次复用
5Token 缓存相同前缀 90% 折扣（Claude + OpenAI 均支持）

Chapter 03

Knowledge vs Skills 解耦

两级渐进式加载 · 上下文效率 · 可维护架构
最常见反模式
把所有能力（角色 + 规则 + 工具说明 + 领域知识）塞进一个超长 System Prompt → 10,000+ tokens 每次消耗，注意力稀释，脆弱难维护。

正确架构：两层分离

层级文件内容加载时机
身份层AGENTS.md / System Prompt角色、行为规则、约束策略始终加载
能力层SKILL.md 文件集领域专项能力、工具调用方式按需动态加载

渐进式披露（Progressive Disclosure）

Level 1 — 扫描阶段（极低成本）
  Claude 只看 Skill 的【名称】和【一行描述】
  → 判断是否与当前请求相关
  → 成本：每个 Skill 仅几个 tokens

Level 2 — 加载阶段（只加载匹配的）
  加载完整 SKILL.md 详细指令
  → 包含步骤、示例、工具配置
  → 不匹配的 Skill 永远不消耗上下文

核心收益

💰 上下文效率
只有相关技能被加载，保留宝贵的上下文窗口给真正有用的信息
♻️ 可复用性
同一个 Skill 可被多个 Agent 共享（如代码审查 Skill 被调试/PR/生成三个 Agent 共用）
🔧 可维护性
修改某个 Skill 不影响 Agent 身份，变更隔离，风险极低
📈 可扩展性
添加新 Skill 无需重建 Agent，系统容量线性增长

多 Agent 系统级应用

规划 Agent    ← 加载 [规划Skill] [领域知识Skill]
执行 Agent    ← 加载 [工具调用Skill] [代码执行Skill]
验证 Agent    ← 加载 [质量标准Skill] [测试Skill]

各 Agent 身份独立，Skill 按需共享
⚠️ 供应商锁定警告
Claude Agent Skills 标准（2025-12 发布）是 Anthropic 专有标准。为 Claude 构建的 Skills 无法直接迁移到 GPT 或 Gemini。生产系统请考虑抽象层。

Chapter 04

上下文工程与提示词设计

范式转变 · ReAct 框架 · 模型类型匹配策略

范式转变：提示词工程 → 上下文工程

维度提示词工程（旧）上下文工程（新）
关注点如何措辞在上下文中放什么信息
目标让模型输出正确格式用最少 tokens 最大化期望输出概率
层级单次交互优化整个 Agent 系统的信息架构
Andrej Karpathy 的定义（2025）
"上下文工程是一门微妙的艺术与科学——用恰好合适的信息填充上下文窗口，以最大化下一步的期望输出概率。"

针对不同模型类型的策略

推理型模型（Claude Extended Thinking, o1）：
  → 给高层目标，信任模型自行分解细节
  → 类比：告诉资深工程师"要解决什么"
  例：「实现一个高并发消息队列，考虑各种边缘情况」

指令遵循型模型（Claude Haiku, GPT-4o）：
  → 给明确的分步指令
  → 类比：给初级工程师写详细任务清单
  例：「1.创建文件 2.添加类 3.实现方法 4.写测试」

ReAct 框架（思考-行动-观察循环）

Thought:  [分析当前状态，确定下一步]
Action:   [工具名称]
Action Input: {"参数": "值"}

收到结果后：
Observation: [工具返回的内容]
Thought:  [基于结果的新分析]
...（循环至任务完成）

Final Answer: [最终答案]

自我批评循环（Self-Critique）

1. 生成初始输出
2. 批评："这个输出有什么问题？"
3. 基于批评修改
4. 重复直到质量达标
效果数据
系统性使用自我批评循环，某些工作流效率提升 60-70%。

实用上下文优化策略

场景低效做法高效做法
代码库分析一次性加载所有文件动态加载相关文件（RAG）
长对话保留全部历史定期压缩，保留关键决策节点
工具文档全部工具说明放 Prompt技能路由，只加载相关工具
多轮调用每次重发完整上下文利用缓存，相同前缀 90% 折扣

软件工程原则在 Agent 系统中的应用

SOLID · OOP 映射 · 知识管理分层架构

SOLID 原则映射

原则Agent 应用
S 单一职责一个 Agent 一个领域，不做"全能 Agent"
O 开闭原则通过新增 Skill 扩展能力，不修改 Agent 核心身份
L 里氏替换专化 Agent 可替换通用 Agent 而不破坏系统
I 接口隔离工具接口精确匹配 Agent 需求，不暴露无关接口
D 依赖倒置Agent 依赖工具抽象（MCP），不依赖具体实现

OOP 概念映射

OOP 概念Agent 架构应用
封装自包含的 Agent 模块，有界的数据与方法
多态运行时动态切换行为（策略模式）
继承基础 Agent 类扩展为专化 Agent
抽象高层行为隐藏实现细节

┌─────────────────────────────────────────────────┐
│  Layer 6 - Working Memory（工作记忆）             │
│  → Context Window（精心策划，非填满）              │
├─────────────────────────────────────────────────┤
│  Layer 5 - Retrieval（检索层）                   │

├─────────────────────────────────────────────────┤
│  Layer 2 - Graph Memory（图记忆）                │
│  → Knowledge Graph（Neo4j / AWS Neptune）       │

为何 PostgreSQL + pgvector 成为 2025 年标准？
三笔大额收购证明市场方向：Snowflake 收购 Crunchy Data（2.5亿$）、Databricks 收购 Neon（10亿$）、Supabase E 轮（1亿$）。pgvector 扩展让 PostgreSQL 直接支持向量搜索，无需额外引入专用向量数据库。
重要警告
当前 LLM 对抽象软件工程原则的理解有限。不要依赖模型自动应用 SOLID 原则——架构师必须在系统设计阶段手动强制执行，把 Agent 当作精心设计的软件系统中的组件来对待。

自进化 Agent 前沿框架

Darwin Gödel Machine · RoboPhD · GEPA · 安全考量

进化设计三个维度

维度选项
进化什么模型参数、提示词、记忆、工具集、工作流图、Agent 群体角色
何时进化任务内（测试时反思、在线RL）或跨任务（跨episode微调、进化搜索）
如何进化梯度RL、模仿学习、种群进化算法、元学习

四大核心框架

🧬 Darwin Gödel Machine
维护代码库版本树。只有实证超越先祖性能才被接受。开放式进化 + 可量化安全性。目前最接近"真正自我改进"。
🎓 RoboPhD（2026-01）
实例化 → 跨污染 → ELO 锦标赛 → 错误驱动 Artifact。产生了在任何先前基准中都不存在的涌现能力。
🔄 GEPA（OpenAI Cookbook）
采样轨迹 → 自然语言反思 → 提议提示词修订 → 帕累托评估。可直接实现的提示词自动优化循环。
🏭 EvoAgentX（EMNLP 2025）
自动化 Agentic 工作流进化框架。在 EMNLP'25 展示，有开源实现（GitHub）。

GEPA 核心循环（可直接使用）

def gepa_loop(agent, task_samples, iterations=10):
    current_prompt = agent.system_prompt

    for i in range(iterations):
        # 1. 采样执行轨迹
        trajectories = [agent.run(t) for t in task_samples[:5]]

        # 2. 反思（自然语言分析失败原因）
        reflection = reflect_on_trajectories(trajectories)

        # 3. 提议修订
        revised = propose_revision(current_prompt, reflection)

        # 4. 帕累托评估（多目标，不能退步）
        if is_pareto_better(eval(revised), eval(current_prompt)):
            current_prompt = revised

    return current_prompt

安全考量（必须遵守）

自进化系统强制安全要求
  • 必须有版本回退机制（进化失败时能回退到已知良好状态）
  • 代码/模型更新前必须实证证明性能提升，不允许假设
  • 所有进化实验必须在沙箱环境中执行
  • 设置性能下限阈值，低于阈值自动拒绝变更
